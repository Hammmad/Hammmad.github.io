Selected work

Engineering on a large enterprise platform

Scheduling, operations, real-time communication and data exchange — built for a US healthcare software company.

On what's shown

This work was built for an employer, so there's no source code, no internal architecture and no client data here — nor should there be. What follows is the engineering described: the problem, the decision, the trade-off, the result. Happy to go deeper in conversation.

Cutting first load from over twenty seconds to under seven

25 MB build output → 5 MB over the wire, and a clinical app that stopped making staff wait between patients.

+

The platform had grown to roughly 25 MB of uncompressed build output. On the connections our users actually had, it took twenty to thirty seconds before anyone could do anything — which, for staff working between patients, is the difference between a tool and an obstacle.

I'd built the application, so I knew where the weight was rather than needing to hunt for it: four of the heaviest dependencies were internally developed modules pulled in by git reference, loaded up front even though most users never reached them. Moving them behind deferred imports took the build from 25 MB to 18 — a 28% reduction, and the architectural half of the work.

The other finding was that the application was being served with no compression at all. Once configured, transferred size came down to 8 MB with gzip and 5 MB with brotli, which is what most browsers receive.

The trade-off is a brief load the first time a user opens a deferred module, covered by a loading state — a fair exchange for the first-paint cost it removes for everyone, every time.

A metadata-driven UI framework — and a boundary around it

Half the build time per standard screen, and a UI that stayed consistent as the team grew.

+

Enterprise products are mostly the same screens repeated: list, create, edit, view. Ours were being rebuilt by hand each time, slightly differently each time, and the inconsistency compounded across teams.

I designed a framework that renders those screens from metadata. A developer declares the endpoint and action, the layout type, and the columns or fields they need; a loader widget takes that description and renders the screen. Pagination, search and accessibility are implemented and tested once, inside the framework, so every new screen inherits tested behaviour instead of each developer re-implementing it.

The decision I'm most pleased with is what it deliberately does not do. It covers a defined set of screen types and nothing else. Anything outside that drops to a centralised library of generic components and is composed by hand. Scoping it that way is why it stayed useful instead of becoming a system everyone fights.

It's also not tightly coupled to one API shape: key mappings have defaults, any action or capability can be overridden, and a service that genuinely needs a different structure gets a second version rather than breaking the framework.

Automated quality gates across the organisation's repositories

Standards, performance, accessibility and tests enforced in CI — not in people's heads.

+

Standards that live in a wiki decay. Standards that live in a pipeline don't. I set up the Bitbucket Pipelines configuration across our repositories so that coding-standards checks, performance checks, accessibility checks and the Flutter test suite all run automatically on every change — which means a pull request arrives already filtered, and review time goes to design decisions instead of formatting arguments.

Accessibility in CI is the one I'd point at. Most teams treat accessibility as something a designer raises late or nobody raises at all; putting it in the pipeline makes it a build condition rather than an opinion.

I also own the release flow on the frontend side: feature branch into dev, tag the dev branch and deploy to a dev environment for testing, then the same feature branch into main, main into release, and a tag to deploy. Our DevOps team runs the deployments; the frontend team owns the releases and what goes into them.

It's also the backstop for generated code. A pipeline that fails on standards, performance and accessibility catches a whole class of problem before a human ever reads the diff.

A form builder, for users rather than developers

Clinical teams compose their own forms; the app renders them at runtime. Built on Bloc.

+

Clinical teams need forms nobody can predict in advance — intake questionnaires, assessments, consent flows that differ by practice. Shipping a release for each one was never going to scale.

I built a form builder that moves that power to the user: forms are composed visually, with configurable fields and validation rules, and the application renders those user-defined forms at runtime. The same data-defined UI idea as the framework above, aimed one level further out.

Built on Bloc rather than the product's older state management, because a widget tree whose shape is determined at runtime needs state transitions you can trace and test. Explicit event-to-state flow earns its boilerplate when the UI itself is dynamic.

+

The platform's real-time layer — chat, audio and video calling on LiveKit, SMS integration and push notifications — inside an application that also has to satisfy constraints on what may be logged and stored. How I work now

AI-assisted code, and the review that has to follow it

A great deal of frontend code is now generated. The scarce skill is no longer producing it — it's deciding what survives review.

I work with Claude, Cursor and MCP-integrated workflows daily, and so does the team. I review the pull requests of seven to eight engineers, which means I'm the point where generated code either enters the codebase or doesn't. The discipline is the one you'd apply to a capable junior's PR: read every line, check the API exists and isn't deprecated, ask what it does under load, and reject anything the author can't explain.

I decline suggestions for three recurring reasons: it builds a generic widget where the codebase needs a reusable one; it solves the problem locally with no regard for reuse; or — the one that matters most — it fixes the reported bug without accounting for the other features depending on that code, so the fix would break something else.

That last failure is the argument for the framework work rather than against it. I treat it as three layers: codified patterns and a shared component library constrain what gets generated; a CI pipeline fails the build on standards, performance and accessibility before a human reads the diff; and review catches what neither can. Generated code defaults to solving the problem in front of it — a codebase needs the systemic answer.
